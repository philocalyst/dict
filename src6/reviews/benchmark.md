# LEX6 benchmark evidence plan

Status: complete for the bounded evidence runs below.  The timing rows were
run only after the exact root quiet-gate authorization.  Earlier exploratory
rows without compiler barriers are superseded and are not used here.

This review owns the independent comparison harness in `src6/bench/`.  The
live LEX6 production tree and the frozen LEX5 borrowed-core tree are inputs;
they are not edited by the harness.  The default smoke and prepare modes do
not call a clock.  Measured mode refuses to start without the exact root
authorization token `ROOT-EXPLICIT-QUIET-GATE`.

## Question being tested

For an honest, explicitly bounded `entry/headword/definition` projection,
does the LEX6 typed packet/archive path have a useful storage or reader
trade-off against the frozen LEX5 borrowed-core path?  This is not an OLD/
SLOB parity test, not a full TEI/LIFT import claim, and not a claim about all
previous five-fixture numbers.

The primary workload is `N=2048`, with exact unique IDs and headwords and one
definition payload per entry.  The default distribution is three repetitive
definitions to one ordinary prose definition; repetitive-only and
prose-only controls can be selected explicitly.  The `rich` profile is a
separate source-rich mixed-content check and is never pooled with primary
rows.

## Input equivalence and bridge

LEX6 receives one `model.Entry` per logical entry, with a typed
`.definition` item and the generated headword/ID.  The flat matched lane uses
the public library container with an explicit empty resource list.  The
separate rich lane supplies scaled independent `Source` resources and entry
origin anchors through that same container; neither lane silently drops
resources.

The frozen LEX5 lane receives the same generated ID/headword/definition bytes
as an original `model.Input`: an `.entry` record (`written=headword`,
`external_id=.text`), a `.definition` record (`written=definition`), one
headword key, and source-document occurrences/bindings.  The documents and
bindings are the canonical old source-backed route for
`sources(.realization).descendants(.definition).texts()`.  One
`definition` predicate/fact links each entry record to its definition record;
this is retained as an old-graph structural link and is not counted as an
extra LEX6 field.  Thus both readers answer the same plain-text projection,
while the report keeps the implementation bridge visible.

The rich profile adds nested inline markup/source occurrences and checks plain
rendering separately.  It is explicitly source-rich correctness evidence,
not a TEI latency claim.

## Required phases

Each lane and input mode keeps these phases separate:

1. Build, with complete archive bytes and SHA-256 retained.
2. Open, which must validate metadata/index/directory only; no LEX6 page is
   decoded in this phase.
3. Full verification (`verifyAll`), including every page digest, decompression,
   packet decode, semantic validation, and index reconstruction.
4. Cold load: page digest, decompression, packet decode, and entry validation
   for selected entries.  The old lane's source-backed read is reported as a
   labelled control boundary because LEX5 has no compressed entry pages.
5. Warm query: already loaded typed-field selection plus render; load/decode
   time is not blended into this row.
6. Exact lookup and prefix enumeration, consuming every hit (entry ID,
   spelling, and optional form) into a digest.  Prefix interval and full
   enumeration remain distinct.
7. Snippet, with an explicit UTF-8-safe bound, separately from full render.

The old `open_metadata` row measures construction of a pending view; the old
Book becomes query-ready only in the separate `verify_all` row.  LEX6
`Archive.open` validates its hot metadata/index/directory and is query-ready
without page decoding, while its full packet/index reconstruction is kept in
`verify_all`.  These differently admitted startup kernels are retained as
boundary evidence, not as a direct startup speed ranking.

The reported cold row is a fresh entry/codec load over the already
memory-resident archive bytes in the same process.  It is not a disk-cold
measurement and includes no file-read latency; the selected entry is decoded
and validated anew for each sample.

LEX6 compression modes are run on identical generated bytes: `raw`,
`adaptive`, and forced `bzip3`.  Adaptive selection is reported as the mode
actually chosen by the archive; a formula or identity stub is not accepted.
The vendored bzip3 path's C allocations are not re-labelled as Zig
allocator traffic.  Normal allocation remains enabled and any codec
admission allowance is identified as accounting, not observed allocation.

## Correctness gates before timing

The no-clock runner must first pass all of the following:

* source and frozen-root manifests unchanged before/after compilation;
* source hash and binary hash retained for every optimization mode;
* nonempty artifact and complete artifact-byte/hash ledger;
* `Archive.open` and `Archive.verifyAll` success for every LEX6 mode;
* exact/prefix hit counts and observed digests equal the independently
  generated logical oracle;
* every LEX6 loaded entry's ID/headword/definition validates and renders to
  the generated bytes;
* old source-backed lookup, enumeration, render, and snippet produce the same
  projection digest;
* no expected answer, digest, or full query schedule is sent to either lane.

The independent digest is only a comparison oracle.  The reader work is
still performed and consumed; returning a precomputed answer is forbidden.

The final runs used ReleaseFast, `N=2048`, two warmups and seven measured
samples per repeated reader phase.  Build and open are intentionally one
observation each; they are not presented as stable speed rankings.  Every
stage retained `raw/runner.stdout`, `raw/runner.stderr`, the executable,
`provenance.json`, and the complete artifacts:

| rich / mixed | `src6/bench/evidence/rich-mixed/` |
| flat / prose | `src6/bench/evidence/flat-prose/` |

`5bee6e5ba1e27f4d25abb44159e39f971dfe3f38004e69b567494e76af62c576`, before

warm render/snippet totals are only hundreds of nanoseconds over seven calls
and are below reliable resolution on this clock path; they are retained as
raw observations and must not be turned into precise warm-speed ratios.

The N=2048 rich/mixed raw row is copied from the exact before/after table
above.  The four-size table is a bounded structural check, not a fitted
complexity law; each build and full-verify value is a single observation.

The cold boundary is unchanged from the baseline: a fresh selected-entry
load over memory-resident archive bytes, including page digest,
decompression, packet decode, and semantic validation.  It is not disk-cold
and does not include file-read latency.  The old source-backed control still
has no compressed entry-page boundary and remains a narrower, differently
admitted operation.  The source-scope fix and the artifact identity result
therefore do not justify a new cold-load comparison or a universal startup
claim.

The synthetic prose strings are fixed templates with deterministic index
substitution, not a natural-language corpus.  The result supports only the
bounded matched projection and the separate rich source/resource check.

The harness is ready for a future query-scope review: the current evidence
covers only exact headword lookup, two nonempty prefixes, a missing prefix,
all-hit consumption, definition render, and bounded snippet.  Any additional
forms, languages, relations, resource kinds, or source-import semantics need
their own equivalence mapping and correctness gate before timing.

## Timing authorization and analysis questions

Before root supplied the quiet gate, only compile, smoke, and semantic
correctness preparation were allowed.  After authorization, one bounded run
per declared mode/configuration was enough to collect evidence; no retry loop
or noise-chasing reruns should be inferred.

The evidence above answers, separately and with raw observations:

* Are complete artifact bytes smaller or larger, and by how much per codec?
* Does `open` stay page-decode-free as designed?
* What are cold load, full verification, and warm query costs when their
  boundaries are kept distinct?
* Does LEX6's compressed page work change the storage/read trade-off across
  repetitive and prose controls?
* Do exact/prefix counts, all-hit digests, full render bytes, and snippets
  remain identical on the matched subset?
* Which findings are only LEX6-vs-frozen-LEX5 subset observations, and which
  are unavailable because the old/new semantic models differ?

No universal speedup, dramatic LOC reduction, OLD parity, or complete
interoperability conclusion may be derived from this harness alone.
